# 战斗差异化 v0.18.0 验收

发布状态：2026-10-10 已部署 v0.18.0 至唯一 Docker 8080，开发验证通过，待用户体验验收。入口：内部局域网服务 。刷新网页并重新登录；更新前停留在大厅的旧登录会话已失效。

## 上线后建议体验

进入“自由试用”→“首领演练”。首领按咖啡炉、碎纸机、打印机、冲压机、巨蟹本体、审计形态、过载形态轮换；击败后稍等下一只。此处均为完整招式，冒险早期会逐步简化。

1. **看动作躲攻击**：近身攻击不再铺通用警告圈。观察抬钳、压低身体、张开齿口和喷嘴蓄力；远处盖章仍显示落点。判断是否既有压力，又能看懂。
2. **试不同走位**：咖啡炉先避喷射，再处理液体环和近身沸腾；打印机横移后再次推纸浪；冲压机第三次会追打旧落点。判断各首领是否需要不同应对。
3. **试反击**：巨蟹绕背、碎纸机打侧面电机、打印机绕后、咖啡炉打正面阀门。轻击后不一定有弱点，重招与连招后再抓机会。
4. **看真实命中**：移动波走到面前才造成伤害；跳过环、横移躲浪；怪物被打断或消失后，残留攻击载体应及时清理。
5. **试小怪与联机**：野外快递突进、盾击与破坏型的动作、节奏应不同；钓获生物仍是低风险来源。与队友看同一次攻击，检查方向、命中和弱点反馈是否一致。

## 联机性能范围

冻结候选0.18.0、独立Docker18083、1280×720、WebRTC直连，八名参与者由一个真实Godot网页画面和七个独立协议虚拟玩家组成。60秒夜战最多18只怪物，观察到3组咖啡炉完整三连，帧间隔P95为16.75毫秒、最大80.23毫秒，各参与者指令往返P95最高60.42毫秒。画面指标是浏览器RAF间隔，不等于GPU耗时；同机环回数据不能代表八台真实电脑或公司网络的延迟上限。

专项场景从首领49%血量及完整招式开始，保持正常伤害、资源、生成上限和运行速度；机器人先观察连招约32秒，再恢复战斗。七形态轮换和该受控夜战不用于证明最终难度平衡。

测试进程树60秒样本峰值工作集2.44 GiB、提交2.14 GiB；整机CPU峰值54.76%、最低物理余量4.67 GiB、最低提交余量7.08 GiB。Docker/WSL另行监控。显式无人使用授权只免除初始空闲等待，本轮未触及低于4 GiB的物理余量，不能宣称验证了更低余量下的稳定性。

补充120秒稳定性复验通过：夜战连续约96.91秒，自然进入整备约21.52秒，八名队员保持在线，首领完成4组三连，RTC通道关闭0次。帧间隔P95为16.74毫秒、最大80.26毫秒，指令往返P95最高67.26毫秒。该样本进程树峰值工作集2.36 GiB、提交2.29 GiB；整机CPU峰值57.15%、最低物理余量4.63 GiB、最低提交余量7.03 GiB。未触发资源保护停止。

两轮正式样本的外部监控中，Docker/WSL工作集最高约0.80 GiB，自有进程的单个GPU引擎读数最高43%；该读数不是所有GPU引擎总利用率。

早期短测曾因部分协议队员没有操作指令而缺失RTT，已加入正常切枪采样；另一次发生直连转中转，主机仍保留八人，根因未能从当时日志确认。加入RTC事件记录后的短测、60秒及120秒样本均未复现，仍保留失败记录，不宣称原偶发事件原因已修复。首次120秒样本的换弹检查超时还暴露测试器未及时捕获异步失败、未处理空装备的缺口，修正后完成上述复验；失败样本不算通过。
